## 3. 前端状态变化

### 3.1 前端状态与业务状态的边界

这是本节最重要的声明：

| 维度 | 前端状态 | 业务状态 |
| --- | --- | --- |
| 定义者 | 成员 4、9 | 成员 3、8 |
| 存在位置 | 浏览器内存、URL、本地存储 | 服务端数据库 |
| 示例 | 加载中、已展开、草稿未提交 | `PENDING`、`APPROVED`、`REJECTED` |
| 权威性 | 不具权威性，刷新可重建 | 权威，界面须以其为准 |

**规则**：前端状态不得覆盖或推测业务状态。两者不一致时以服务端返回为准并提示用户。

### 3.2 五类前端状态

| 类别 | 编号前缀 | 含义 |
| --- | --- | --- |
| 数据加载状态 | `FS9-L-*` | 数据请求的生命周期 |
| 用户输入状态 | `FS9-I-*` | 表单与控件的输入过程 |
| 视图呈现状态 | `FS9-V-*` | 展开/折叠、标签切换、布局模式 |
| 会话权限状态 | `FS9-A-*` | 登录态与可见能力 |
| 业务映射状态 | `FS9-B-*` | 业务状态在界面上的呈现（只读映射） |

状态优先级：无权限 > 加载失败 > 加载中 > 业务映射 > 视图呈现 > 用户输入。同一区域出现多个状态时按此优先级呈现，避免矛盾反馈。

### 3.3 数据加载状态

| 编号 | 状态 | 界面表现 | 禁止 |
| --- | --- | --- | --- |
| `FS9-L-IDLE` | 空闲 | 显示任务入口与示例 | 不显示"0 条结果" |
| `FS9-L-LOADING` | 加载中 | 保持框架稳定，超 300ms 才显示指示 | 不允许重复触发同一提交 |
| `FS9-L-SUCCESS` | 有数据 | 显示结果、条件、数据版本 | 不隐藏当前筛选条件 |
| `FS9-L-EMPTY` | 业务空 | 明确无匹配 + 可操作修正 | 不写成服务异常 |
| `FS9-L-ERROR` | 依赖失败 | 可识别错误 + 重试 + 追踪标识 | 不伪装成 `total=0` |
| `FS9-L-STALE` | 版本失效 | 提示重新查询，保留已见内容 | 不混用旧分页结果 |

状态机图：[frontend-load-state.puml](../../contributions/member-09/analysis/diagrams/frontend-load-state.puml)

### 3.4 业务映射规则

| 编号 | 规则 |
| --- | --- |
| `FS9-BR-01` | 前端缓存与服务端返回不一致时以服务端为准并刷新 |
| `FS9-BR-02` | 提交后不本地推断结果，须以服务端权威状态渲染 |
| `FS9-BR-03` | 通知失败不得使已提交操作显示为未提交 |
| `FS9-BR-04` | 记录被他人先处理时提示已更新并加载权威状态，不覆盖 |

## 4. 异常反馈分析

### 4.1 为什么需要独立分析

问卷显示 96% 用户关注数据来源、94% 关注更新时间（`E-B-Q-001`）。异常被错误表达为正常数据会直接损害信任。本节目的：防止不同性质异常被混为一谈、防止反馈泄露隐私、为每类异常给出可执行恢复路径。

### 4.2 六类异常

| 编号 | 类别 | 原因归属 | 用户可否自行解决 |
| --- | --- | --- | --- |
| `EX9-C1` | 业务空结果 | 无人出错 | 可以（改条件） |
| `EX9-C2` | 用户输入错误 | 用户 | 可以（改输入） |
| `EX9-C3` | 权限不足 | 规则限制 | 部分（登录或申请） |
| `EX9-C4` | 业务冲突 | 并发或状态变化 | 可以（刷新后重试） |
| `EX9-C5` | 依赖失败 | 系统 | 不能（只能重试） |
| `EX9-C6` | 数据不完整 | 数据源 | 不能（可反馈） |

### 4.3 必须区分的三组

| 易混淆 | 判别依据 | 混淆后果 |
| --- | --- | --- |
| 业务空 vs 依赖失败 | 服务是否成功响应 | 把失败显示成"0 条"，用户误以为真无数据 |
| 输入错误 vs 依赖失败 | 错误是否可由修改输入消除 | 把输入问题显示成系统错误，用户反复重试 |
| 数据缺失 vs 真实值为 0 | 字段是否存在 | 把"未知"显示为"0"，产生错误结论 |

`EX9-R-01`：以上三组必须使用不同视觉与文案，不得互相替代。

### 4.4 隐私敏感的反馈设计

| 场景 | 不安全的反馈 | 安全的反馈 |
| --- | --- | --- |
| 访问他人申请详情 | "该申请属于其他用户" | "无访问权限" |
| 访问不存在的申请 | "申请不存在" | "无访问权限"（与上一条相同） |
| 门户已被他人认领 | "已被用户 X 认领" | "该门户已被认领" |

`EX9-R-03`：对"无权访问"与"不存在"使用相同反馈，使攻击者无法通过反馈差异推断记录存在性。

### 4.5 数据不完整的三种表达

| 情况 | 含义 | 界面表达 | 禁止 |
| --- | --- | --- | --- |
| 未提供 | 数据源未给该字段 | "未提供" | 不显示 0、不留空白 |
| 未知 | 字段存在但值不可确定 | "未知" | 不显示 0 |
| 真实为 0 | 确实是 0 | "0" | 不显示"未提供" |

统计页面若有未知类数据，必须显示未知类占比，否则用户对分母产生错误理解（`EX9-R-10`）。

## 7. 方案 A 与方案 B 的处理

### 7.1 已识别的共同基线

两组表述一致，建议直接写入统一文档正文，不列为差异：

1. 登录成功不等于认领成功，申请创建不等于获得维护权
2. 前端隐藏不替代服务端授权校验
3. 业务空结果与依赖失败必须可区分
4. 权限反馈不泄露记录存在性
5. 并发冲突时以服务端权威状态为准
6. 未知值不用 0 表达

第 3.4 节的并发规则参照了成员 4 方案 A 需求建模材料第 4 节，两组一致。
