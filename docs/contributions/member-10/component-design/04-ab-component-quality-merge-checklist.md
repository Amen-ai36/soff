# A/B构件设计质量对照与合并前检查（成员10）

## 1. 公共基线不可分叉

| 公共资产 | A/B必须一致 | 变更审批 |
|---|---|---|
| SRS与验收口径 | 是 | 成员1、6共同确认 |
| 公共业务实体与ID语义 | 是 | 成员1、6共同确认，相关模块复核 |
| OpenAPI路径、方法、字段和错误码 | 是 | 成员1、6共同确认，成员3/8实现 |
| 状态枚举、分页和空值语义 | 是 | 成员1、6共同确认 |
| 测试夹具、预期结果和严重级别 | 是 | 成员1、6与成员5/10共同维护 |
| 内部表结构、算法实现、缓存实现 | 可不同 | 需保持公共语义并记录适配成本 |
| UI内部组件、布局实现 | 可不同 | 需满足共同交互与可用性验收 |
| 构建工具/命令/制品格式 | 可不同 | 记录实际版本与可重复构建证据 |

## 2. 逐构件对照项

- 数据库：公共实体字段语义一致；迁移可追踪；约束与事务可验证；备份恢复策略明确。
- 检索：公开过滤一致；空结果/依赖故障区分；分页排序稳定；索引可重建。
- API：公共OpenAPI契约一致；鉴权和错误语义一致；异步任务可追踪、幂等。
- ETL：来源追溯、低置信隔离、重复批次不重复计数、失败恢复一致。
- UI：关键页面状态、认领授权语义、错误提示和隐私边界一致。
- 统计：统计对象、分母、去重规则和版本口径一致。
- 工程：构建可复现；测试报告关联提交；制品可追溯；部署可回退。

## 3. 合并选择原则

按照团队总方案，先用同一数据集和公共测试验收A、B；按功能完整性、缺陷数、覆盖率、性能、代码质量、文档和部署稳定性评分；选择综合得分更高的一组作为主版本进入 `integration`，再通过公共接口、适配器或策略模式逐个迁移另一组优秀模块。每迁移一个模块立即执行契约测试和完整回归。不能把两组完整系统机械拼接。

成员10应提供：流水线运行结果、测试报告、覆盖率、部署记录、回滚演练、缺陷统计和运行稳定性证据。没有真实执行记录的维度标记“待验证”，不参与伪造评分。
