## 2. 统一规则检查

- [ ] R01—R15编号与统一追踪表一致；成员局部编号保留来源前缀，不凭相似标题强行合并。
- [ ] 每个功能需求至少能映射到一个用例或业务流程，并有可验证的验收条件。
- [ ] 每张图都有图号、标题、版本、来源文件、责任人和对应需求编号。
- [ ] 认领状态、采集任务状态与文字SPEC中的状态名称完全一致。
- [ ] 图中出现的角色与SRS角色定义一致；管理员审核自己的申请等冲突场景有明确约束。
- [ ] 数据规模“至少10,000条”被当作验收要求；建议类型配比、质量阈值不能误标为教师硬性要求。
- [ ] PlantUML/SVG只标为提案或参考图，除非确实在CodeArts完成并保留平台源文件，否则不写“CodeArts建模已完成”。
- [ ] 需求状态采用“草案/待确认/已批准/已实现/已测试”等区分，不能用“文档已存在”替代“需求已验收”。

## 3. 评审问题关闭规则

问题关闭至少要包含：问题编号、确认人、实际日期、决定内容、受影响文件、验证证据。未开会的事项不能写成“会议决定”；未取得教师意见的事项不能写成“教师已确认”；仅提出建议不等于问题已关闭。

## 4. 本轮检查结论

从所提供文件可见，项目已具备需求调研统一初稿、部分总体用例/流程提案和成员贡献材料；仍需完成公共编号与状态规则统一、数据处理SPEC补齐、正式CodeArts模型交付、需求追踪汇总及人工评审。当前状态是“可继续汇编和评审”，不是“需求建模验收通过”。
