## 3. 成员 5 本次已经整理的内容

### 3.1 部署口径

- 浏览器只访问 HTTPS 入口，不直接访问 RDS、OBS、CSS
- RDS 保存成果元数据、认领状态、任务账目和审计信息
- OBS 保存原始批次、处理产物和受控证明对象
- CSS 只保存公开检索投影，不能作为认领证明的权威来源
- 采集与 ETL 作为异步 Worker，重试依靠批次号、幂等键和版本检查
- 当前只把 ECS/CCE 写成候选部署组件，不能说已经创建云资源或完成高可用部署

### 3.2 答辩可讲的测试数据

这些数字来自统一 SRS 和已经归档的问卷汇总，可以作为“为什么要这样设计”的依据：

- 问卷共 50 份：本科生 22 人、研究生 20 人、教师/科研人员 6 人、其他 2 人
- 48/50 关注来源，说明成果必须保留来源和更新时间
- 40/50 受访者提到同名困扰，说明不能只按姓名合并作者
- 45/50 希望在详情页看到认领入口，说明检索、门户和认领需要连起来
- 38/50 希望在搜不到时得到相似词或替代提示，说明正常空结果和依赖故障必须区分
- 课程目标是不少于 10000 条成果，但目前材料不能证明已经达到这个规模，因此 PPT 只写“目标”，不写“已完成”

### 3.3 五个代表性验收场景

答辩时可直接用下面的输入—预期说明，不要说成已经通过测试：

1. 同一批次重复处理：规范成果数量不增加，批次和版本仍可追溯
2. 低置信度同名记录：不自动合并，进入隔离或人工复核
3. 同一门户并发认领：最多一个有效授权，失败申请不留下半授权
4. CSS 延迟或故障：返回明确的依赖异常，不显示成“0 条结果”
5. 权限收紧或撤回：当前页、total、排序和统计分母都不能继续泄露旧数据

## 4. 答辩前必须找队友确认的三件事

1. 组长确认 PPT 首页的组号、队名、成员姓名和讲解顺序
2. 成员 1、6 确认公共服务名、A/B 方案差异和至少 3 条 ADR 的最终文字
3. 实际建模成员确认 CodeArts Modeling 是否已经导出正式逻辑架构图和部署拓扑图；若没有，答辩时只能说“候选设计，待正式建模”，不能说已完成

## 5. 不能在答辩中说的话

- “已经上线”“已经完成高可用部署”
- “流水线已经全部跑通”
- “系统已经支持 10000 条成果”
- “A 组一定比 B 组效果好”
- “PlantUML 图片就是 CodeArts 源文件”

这些说法目前没有对应的真实运行或平台证据
