# 测试与部署输入清单

日期：2026-10-21。用途：把需求分析阶段可复用的验证条件交给后续架构、构件设计与编码；不是部署方案或流水线配置。

## 1. 已可作为测试设计输入的内容

| 测试领域 | 已有分析/需求输入 | 最小可观察结果 |
| --- | --- | --- |
| 数据处理 | 同批次链路、来源追溯、去重成果计数、低置信度不自动合并 | 输入来源与处理版本可反查；重复处理不新增规范成果；隔离记录不进入公开统计 |
| 认证与授权 | 账号不等于学者，申请不等于授权，管理员不得自审 | 未授权访问被拒绝；提交申请不获得维护权；审核通过一次只产生一项有效授权 |
| 认领与维护 | 并发申请、版本校验、原子授权、共享数据治理 | 两次争同一门户最多一次成功；写失败无半授权；个人展示变动不删除共享成果 |
| 检索与统计 | 公开范围、空态/故障区分、冻结版本、统计口径 | 受限成果不出现在结果或 total；依赖失败不伪装为空结果；同版本可复现结果 |
| 采集运行 | 停止、失败、恢复、检查点与批次记录 | 停止后不再启动未处理单元；已提交批次可追溯；恢复不重复计数 |

来源：统一 SRS 第 4～8 节、成员 1 分析追踪、成员 2/7 数据规范、成员 3/8 业务 SPEC、成员 4/9 交互需求。具体文件由[统一 SPEC 目录](../../../deliverables/02-requirements/02-spec-catalog.md)和[模型追踪索引](../../../deliverables/02-requirements/03-model-and-traceability-index.md)统一定位。

## 2. 在写流水线或部署方案前必须补齐的输入

| 缺失输入 | 为什么不能猜 | 需要谁提供 |
| --- | --- | --- |
| 选定技术栈、构建命令、测试命令 | 没有真实命令就不能写能运行的 CodeArts 流水线 | 两组实现负责人和成员 1/6 |
| 环境分层及密钥管理方式 | 不能把真实地址、账号或密钥写入仓库，也不能虚构云资源 | 部署责任人与课程云环境实际操作者 |
| 冻结的 API、错误码、状态枚举与分页格式 | 契约未定时，自动化测试无法定义唯一预期 | 成员 1/6 和各模块负责人 |
| 数据集 manifest、规模计数与模拟数据标记 | “有 10,000 条”要能复算，不能只写在报告里 | 成员 2/7，成员 5/10核对 |
| 两组统一的冒烟/回归场景 | 否则 A/B 通过的不是同一把尺子，不能公平比较 | 成员 5/10 汇总，各岗位审阅 |

## 3. 建议的下一步交付顺序

1. 由成员 1/6 登记本阶段确认后的公共语义与仍未冻结项；不要从旧 PPT 反推接口细节
2. 成员 2/7、3/8、4/9 各自提交可执行测试场景的输入、预期与测试数据边界
3. 成员 5/10 将场景拆为单元、接口、端到端、数据质量和运行保障五类，并建立“场景—责任人—自动化位置—结果”台账
4. 技术栈落地后，再依据真实项目命令配置 A/B 各自的构建、测试、制品与部署流程；不提前编造 YAML
5. 每次候选实现能运行后，使用同一组夹具记录结果、缺陷和版本，形成阶段演示与最终择优依据
