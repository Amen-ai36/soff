# 业务对象边界与职责

版本：0.1，2026-10-19。成员1供稿，待成员6共同确认。

## 1. 分析依据

本包采用成员1既有[总体需求](../requirements/02-actors-and-overall-requirements.md)及[用例说明](../requirements/04-use-cases.md)中的M1-FR、M1-UC编号，结合成员3的[业务章节](../../member-03/requirements/01-srs-contribution.md)、[认领SPEC](../../member-03/requirements/specs/SPEC-M3-CLAIM.md)、[接口语义](../../member-03/requirements/03-interface-constraints.md)，以及成员2的[数据需求](../../member-02/requirements/01-data-pipeline-requirements.md)和[任务状态模型](../../member-02/requirements/03-collection-task-state-machine.md)。来源中的候选规则保留候选状态。

百万级目标依据2026-10-14用户转达的规模反馈及明确要求。本阶段分析怎样保证正确计数、来源追踪和恢复，不指定分库、分片或服务数量。

## 2. 对象清单

下列“识别信息”仅帮助区分对象，不是数据库字段清单。

| 分析对象 | 识别信息与职责 | 明确不承担的职责 |
| --- | --- | --- |
| Account 账号 | 账号标识、会话主体和操作资格 | 不因姓名一致自动成为某学者 |
| Scholar 学者 | 规范学者标识、姓名变体与区分线索 | 不等于登录账号，不按姓名唯一识别 |
| ScholarPortal 学者门户 | 对某学者提供公开展示与受控维护入口 | 不公开认领证明，不拥有成果产权 |
| ClaimRequest 认领申请 | 申请标识、目标门户、申请人、材料引用和审核结果 | 提交申请不直接授予维护权 |
| PortalGrant 门户维护授权 | 将特定账号与门户的有效维护资格关联 | 不授予删除共享成果或维护其他门户的权力 |
| Work 规范成果 | 规范成果标识、类型、公开状态与展示信息 | 不按来源条数或作者人数重复计数 |
| Authorship 成果作者关联 | 连接成果与规范学者，承载署名顺序、证据 | 不依据姓名字符串直接创建确定关联 |
| Organization 机构 | 规范机构标识、名称和别名线索 | 不把机构名当全局唯一键 |
| Field 领域 | 规范领域标识及分类体系线索 | 不把未知值伪装成真实领域 |
| SourceRecord 来源记录 | 来源键、来源版本、许可依据与原始证据引用 | 原始载荷不直接进入公开索引 |
| CollectionTask 采集任务 | 来源范围、处理进度、停止与恢复协调 | 不将一次任务重试当新成果 |
| ProcessingBatch 处理批次 | 有界输入、阶段计数、已提交检查点与失败范围 | 未提交批次不推进成功检查点 |
| GovernanceIssue 治理问题 | 冲突、低置信度关联、公共字段纠错的处理依据 | 不静默覆盖人工修正或丢弃未知记录 |

门户维护授权是为了说明“通过后究竟增加什么关系”的分析对象，并不要求采用独立数据库表。PortalGrant的具体有效期、撤销与转让流程未在本包新增。

## 3. 四个职责区域

| 区域 | 包含对象 | 输入与输出边界 | 后续主要责任人 |
| --- | --- | --- | --- |
| 身份与门户权限 | Account、ScholarPortal、ClaimRequest、PortalGrant | 会话与证明引用输入，申请结果和维护资格输出 | 成员3/8，成员1/6复核权限边界 |
| 成果与科研实体 | Work、Scholar、Authorship、Organization、Field | 接收已治理规范实体，提供公开领域信息 | 成员3/8，与成员2/7核对实体归一 |
| 数据接入与处理 | CollectionTask、ProcessingBatch、SourceRecord | 经许可输入，规范结果及处理证据输出 | 成员2/7 |
| 治理与可追溯 | GovernanceIssue及关联证据 | 接收冲突和纠错，输出可审计处理决定 | 成员2/7、3/8 |

这四个区域表示业务职责，不是微服务拆分决策。页面、控制器、数据库和Elasticsearch属于后续交互或设计视图，不作为本图业务类。

## 4. 生命周期与一致性边界

### 4.1 账号、学者、门户

公开数据可先形成学者和门户，学者尚无账号、门户尚未认领都是合法情形。账号可浏览和申请，只有有效授权才允许维护对应门户。管理员是账号在某操作中的资格，不通过继承Scholar表示。

### 4.2 申请、审核、授权

创建申请只产生待审记录。审核提交时必须再次核对管理员资格、回避、申请版本和门户占用。通过决定、唯一有效授权和必要审计应原子一致；任一写入失败不得出现“已授权但申请仍待审”。驳回不产生授权。重复请求不得新增授权，两个争用同一门户的通过请求最多一个成功。

本包引用成员3候选三态语义，不另设撤回或申诉状态。材料标准及具体公共枚举需联合确认。

### 4.3 规范成果、来源和作者

一项规范成果可来自多个来源，来源更正也不自动产生新的成果身份。未通过许可或质量闸门的来源记录可以没有规范成果关联。署名是成果与学者的关系，作者顺序保留在Authorship中。同名学者保留不同标识，低置信度候选先进入治理。

删除本人门户中的展示关联不删除Work或来源证据。学者所属机构可能随时间变化，不能只凭当前所属机构反推出所有历史成果机构；机构归属应由成员3/8结合来源署名证据细化。

### 4.4 任务、批次与来源身份

一个任务处理多个有界批次。相同来源记录可被不同任务或恢复批次再次观察，所以ProcessingBatch与SourceRecord在概念上是多对多，不用组合关系表达“批次删除就销毁来源证据”。每次观察的时间、输入哈希和处理结果由后续详细模型承载。

批次提交成功后再推进检查点；索引同步失败仍可保留已成功持久化的数据，但不能据此宣称公开链路完成。任务状态沿用成员2模型，不在本包重新命名。

## 5. 百万级目标对分析模型的影响

1. 计数单位是冻结数据版本下满足有效、去重和公开条件的Work标识集合。SourceRecord、Authorship、机构及历史版本分别统计。
2. 同一成果来自两个来源、关联三名作者仍只计一个成果。没有规范化结果的隔离来源计入质量报告，不能计入百万目标。
3. 真实与模拟数据分列，四类成果分别披露，模拟性质和来源证据不能在合并中丢失。
4. 数据库与公开索引应比较同版本成果标识集合，仅两个总数相同不足以证明一致。
5. 检索和统计使用可公开范围；过期索引不得绕过权威公开策略。版本快照如何实现留到架构与构件设计。

## 6. 本阶段暂不决定

不决定成果四类型采用继承还是类型属性、不冻结表结构和外键、不确定角色枚举、不增加正式API、不把图中关联直接视为事务边界，也不确定部署架构。所有新增分析概念只作为后续共同评审输入。
