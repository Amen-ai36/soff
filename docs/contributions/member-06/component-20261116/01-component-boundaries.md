# 构件边界与公共约束（成员6供稿）

## 1. 设计目标

把已确认的业务边界落实为可评审的构件边界：在线请求、长任务、权威业务数据、公开检索投影、受控材料和统计读取各有责任归属；公共语义继续服从统一 SRS/SPEC，具体技术实现由对应岗位提交候选方案。

## 2. 构件分区

| 分区 | 构件职责 | 允许依赖 | 禁止越界 | 负责人/状态 |
| --- | --- | --- | --- | --- |
| Web/API | 会话、参数校验、统一错误和分页外壳 | 认证、业务服务 | 不直连数据库或索引 | 4/9、3/8；待收件 |
| 认证与授权 | 身份会话、角色和门户维护权限 | 权威用户/门户状态 | 不由前端按钮代替授权 | 3/8；待收件 |
| 采集任务 | 任务受理、来源适配、检查点、停止/重试 | 任务库、获准来源 | 不把外部原包直接公开 | 2/7；待收件 |
| 清洗与消歧 | 规范化、去重、作者消歧、处置记录 | 候选批次、规则版本 | 不静默删除不确定数据 | 2/7；待收件 |
| 认领与审核 | 申请、门户对应关系、审核决定和审计 | 权威业务、权限 | 不把申请状态当授权结果 | 3/8；待收件 |
| 检索投影 | 公开合法成果的版本化索引与排序 | 已发布版本、CSS候选 | 不绕过公开策略读旧索引 | 3/8；待收件 |
| 统计 | 同一公开版本的分母、聚合和解释 | 发布版本、统计读模型 | 不用来源行数冒充成果数 | 3/8；待收件 |
| 后台编排 | outbox/任务投递、幂等、候选发布核验 | 权威库、候选索引 | 不在失败时推进公开水位 | 2/7/3/8；待收件 |

## 3. 必须保持的公共语义

- 账号、学者、门户、成果、来源行、认领申请、有效审核决定和审计记录分开表达。
- “成果总数”按已发布版本内唯一成果 ID 计算；来源行、作者—成果关系和申请记录不能直接相加。
- 权威业务写入成功不自动等于公开；候选投影、合法 ID 集合和计数核验通过后才能切换公开版本。
- 公开接口的分页、total、统计和排序必须基于同一公开策略与版本边界。
- 任务停止、失败、重试和成功的状态语义沿用已有采集 SPEC；不得用页面状态替换服务端状态。

## 4. 设计选择边界

成员6只确认“应满足的边界和验收问题”。表名、字段名、URL、错误码、ES mapping、缓存产品、云规格和框架版本必须由对应岗位提出，并经成员1/6共同确认后进入公共资产。
