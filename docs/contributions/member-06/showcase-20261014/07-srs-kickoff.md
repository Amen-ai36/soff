## 3 编号和单条需求格式

本次先保留FR01～FR09总体编号及各作者M8-*、B-U*等局部编号，不强行改名。汇编时增加“正式编号↔原编号”映射，旧引用保持可查。图表也保留原作者编号，统一编号由汇编后核对，避免两个语义相同的需求分配冲突ID。

每条需求按以下字段提交；缺少证据或决定时填“待确认”，不填虚构结论。

| 字段 | 填写要求 |
| --- | --- |
| 原编号、标题、作者、版本 | 可定位原文件及修改责任 |
| 用户目标与需求正文 | 描述系统可观察行为，区分需求与界面方案 |
| 角色、前置条件、触发 | 区分访客、登录用户、已认领学者和管理员权限 |
| 正常、异常及边界流程 | 空数据、无结果、字段缺失、权限不足、冲突及依赖失败分别说明 |
| 输入输出与数据范围 | 引用现有接口提案，不自行定义公共字段或错误码 |
| 来源、优先级、假设 | 课程约束、问卷证据与设计推论分开标记 |
| 关联用例/SPEC/模型 | 保留原ID并注明链接；暂无SPEC则列缺项 |
| 验收场景与条件 | 给出可检查结果；候选指标和实际测试结果分开 |
| 未决问题及复核状态 | 写责任岗位、影响、待确认人；不得代签通过 |

## 5 收件与复核流程

1. 各作者在自己的贡献目录供稿，交接原文件路径、版本、对应章节和未决项；成员6不改动原作者文件。
2. 成员6检查章节覆盖、术语、角色、编号、链接以及用例/状态/SPEC一致性；发现问题进入个人复核表，交原作者修改。
3. 将已接收内容接入唯一SRS，保留来源映射和候选状态；未收到部分标缺项，不以AI代写补齐岗位交付。
4. 成员1复核，成员1、6共同确认公共规则后才能冻结；实际确认人、日期与结论另行记录。
5. CodeArts源文件及清晰导出图与文字对照，PlantUML语义稿不作为平台实操证据。
