# 需求分析 PPT 支撑材料（成员 4）

状态：可并入唯一需求分析 PPT 的页稿；由成员 5/10 统一版式，成员 3 汇编内容，成员 8 复核。以下不是成员 4 单独提交的第二份 PPT。

## 第 1 页：用户与页面关键交互

**标题**：前端视角的关键用例交互

**图表建议**：使用 `diagrams/rendered/01-search-and-view-sequence.png`，右侧保留三条结论。

- 检索链路：输入校验 → 加载 → 有结果/空结果/失败 → 详情或门户。
- 认领链路：未登录先认证并安全返回；创建待审申请后仍不授予维护权。
- 维护链路：个人字段、展示关联、共享成果纠错使用不同操作和反馈。

**讲稿（约 35 秒）**：

成员 4 从用户可观察行为补充关键用例交互。页面只负责建立意图、呈现权威结果和提供恢复动作，不自行创造业务状态。检索空结果与服务故障严格区分；认领提交成功只表示申请进入待审；门户维护还要区分个人展示与公共成果治理。

## 第 2 页：前端状态变化

**标题**：视图状态与业务状态分层

**图表建议**：使用 `diagrams/rendered/03-frontend-view-state.png`，重点放大检索和认领两个区域。

| 页面 | 主要视图状态 | 关键控制 |
| --- | --- | --- |
| 检索 | 初始、加载、有结果、空结果、失败、过期 | 旧响应不得覆盖新查询；不同版本不混页 |
| 认领 | 编辑、提交中、结果未知、冲突、状态展示 | 超时后先查询权威状态；维护权只来自 `APPROVED` |
| 维护 | 未修改、未保存、保存中、冲突、待同步 | 保留草稿，不自动覆盖；保存与公开同步分开反馈 |

**讲稿（约 40 秒）**：

前端加载、冲突、编辑中等是视图状态，不应写入认领业务枚举。业务层当前只引用待审核、已通过、已驳回三态提案。对重复点击、响应乱序、断网和版本冲突，页面都以权威查询结果为准，避免重复申请或覆盖他人决定。

## 第 3 页：异常反馈与可恢复性

**标题**：异常反馈的四个目标

**版式建议**：用四列或 2×2 矩阵，不使用大段文字。

| 目标 | 页面表现 | 代表场景 |
| --- | --- | --- |
| 可识别 | 区分空结果、失败、无权限、结果未知 | 检索服务不可用不显示“0 条” |
| 可恢复 | 提供改词、重试、刷新、登录、查看既有申请 | 重复申请打开原申请 |
| 不丢上下文 | 保留条件和允许的非敏感草稿 | 筛选失败后可继续修改 |
| 不泄露 | 私有申请读取不暴露存在性 | 不显示他人材料和内部审核信息 |

**讲稿（约 35 秒）**：

异常反馈不是统一弹出“操作失败”。输入错误要定位字段，业务空态要给修改入口，写入结果未知要先查询，权限错误要最小披露。所有关键状态都需要可读文字和明确恢复动作，不能只靠颜色或短暂提示。
