# 展现层架构决策记录候选（成员 9，方案 B）

日期：2026-11-11。状态：四条均为 Proposed。成员 6 主编 ADR（方案第 5.4 节），本文为其提供展现层的决策依据；未经成员 1、6 共同确认前不视为团队决策。

编号沿用成员 6 的格式，与其 ADR-M6-ARCH-01～04 不重叠，也不冲突：成员 6 的四条覆盖后端分层、投影一致性、检索版本、部署，本文只涉及浏览器端。

## ADR-M9-01 前端采用 Vue 3 + TypeScript + Vite 单页应用

**背景**

- `AGENT.md` 第 10 节：项目技术栈尚未确定。没有技术栈就无法开始前端实现。
- 展现层要覆盖 13 个路由（公开检索、门户、认领、统计、管理后台），由成员 9 一人在 B 组实现。
- 需求分析阶段已确定大量浏览器端规则：URL 恢复检索条件、最后一次请求获胜、空结果与失败分离等，这些规则需要单元测试，`AGENT.md` 第 7 节要求至少 3 个核心模块行覆盖率 ≥ 80%。
- 成员 6 部署稿中前端与 Web/API 同在 ECS 部署单元，经 HTTPS 访问。

**候选**

| 候选 | 优点 | 缺点 |
| --- | --- | --- |
| A. Vue 3 + TypeScript + Vite（SPA） | 单文件组件把模板、逻辑、样式放在一起，页面多时好维护；Vite 开发服务器启动快；Vitest 与 Vite 共用配置，测试零额外配置 | 首屏需要先下载 JS，不利于搜索引擎收录（本项目无此要求） |
| B. React + TypeScript + Vite（SPA） | 生态最大 | 表单与双向绑定需要更多样板代码；与 A 相比对本项目没有明显额外收益 |
| C. 服务端模板渲染（与后端同框架） | 不需要单独前端工程 | 依赖后端选型，后端未定时前端无法并行开发；交互状态（取消请求、局部刷新）写起来分散 |
| D. 不用框架 | 依赖最少 | 13 个页面的状态与渲染需要自行实现，维护成本高 |

**决策（建议）**

采用 A。版本以 `frontend/package.json` 为准（实施时为 vue 3.5、vue-router 4.6、vite 8、vitest 5、typescript 5.9）。不引入全局状态库和 UI 组件库：本项目的共享状态只有会话一项，组件库会增加视觉规范之外的样式来源。

**后果**

- 正面：前端可以在后端未定时独立开发（配合 ADR-M9-02）；领域规则写成纯 TypeScript，可直接单测。
- 负面：增加一个 Node.js 构建步骤，CodeArts 流水线需要 Node 22.12+ 或 24 的构建环境（成员 10 确认）。
- 风险：若团队最终选择 B 或 C，`views/`、`components/` 需要重写；`domain/` 与 `api/` 是不依赖 Vue 的 TypeScript，可以保留。这是把规则放进 `domain/` 的另一个原因。
- 方案 A 组（成员 4）可能选择不同技术栈，这属于方案第 1 节允许的差异，合并时按功能择优，不要求两组相同。

**验证**

- `npm run typecheck`、`npm test`、`npm run build` 在本地实际通过（结果记在 [实现说明](../implementation/README.md)）。
- CodeArts 构建环境可安装依赖并构建：待成员 10 验证。

## ADR-M9-02 通过 `ApiClient` 接口隔离后端，提供 HTTP 与模拟两种实现

**背景**

- 业务服务层由成员 3、8 实现，接口契约（OpenAPI）尚未冻结。
- 前端需要在后端完成前开发和测试，且契约变动不能波及所有页面。
- 成员 8 已提供合成夹具 `demo-data.json` 及 SPEC 中的预期结果，可用于前端测试。

**候选**

| 候选 | 说明 |
| --- | --- |
| A. 页面直接调用 `fetch` | 最简单；契约一变要改所有页面；测试需逐个拦截网络 |
| B. 引入通用模拟服务（如在浏览器中拦截请求的库） | 页面代码不变；需要额外依赖，模拟逻辑写在拦截规则中 |
| C. 定义 `ApiClient` 接口，HTTP 与模拟各一个实现，启动时注入 | 无额外依赖；页面只依赖接口；契约假设集中在 HTTP 实现中 |

**决策（建议）**

采用 C。页面通过依赖注入拿到 `ApiClient`，默认使用模拟实现；设置 `VITE_API_MODE=http` 时使用 HTTP 实现。

**后果**

- 正面：契约假设（16 项，见 [02 文档第 8 节](02-frontend-backend-communication.md)）只出现在 `api/http.ts`；组件测试无需网络。
- 负面：模拟实现可能与真实后端行为不一致。缓解：模拟实现中检索、统计、认领的规则按成员 8 的 SPEC 编写，并用 SPEC 中的预期结果做测试；后端完成后增加契约测试，以真实后端为准。
- 约束：模拟实现只能出现在开发和测试中，生产构建应设置 `VITE_API_MODE=http`（成员 10 在流水线中配置）。

**验证**

- 测试：`views/` 不得直接引用 `api/http` 或 `api/mock`（架构测试）。
- 测试：模拟实现对成员 8 夹具的检索与统计结果与 SPEC-M8-SEARCH、SPEC-M8-STATS 的预期一致。

## ADR-M9-03 以 URL 作为检索状态的唯一来源

**背景**

- 需求分析阶段要求：后退、刷新、分享后恢复检索条件与分页（UI9-NFR-10、FS9-VR-01）。
- 交互规则：改筛选或排序后回到第 1 页、移除单个条件保留关键词、非法条件不发请求（IA9-RULE-03～05）。

**候选**

| 候选 | 说明 |
| --- | --- |
| A. 状态放在组件或全局状态库，再同步到 URL | 两份状态，需要双向同步，容易出现不一致 |
| B. URL 是唯一来源，页面从 URL 解析出查询，修改条件即修改 URL | 一份状态；浏览器历史天然可用 |

**决策（建议）**

采用 B。`domain/searchQuery.ts` 提供"URL 参数 → 查询对象"（含校验）和"查询对象 → URL 参数"两个纯函数，以及"修改条件"函数（除翻页外一律回到第 1 页）。页面监听 URL 变化后再发请求。

**后果**

- 正面：上述交互规则全部在一个纯函数文件中实现并测试。
- 负面：每次修改条件都会产生一条浏览器历史记录。若用户反馈后退次数过多，可对筛选改用替换历史记录，这只改页面中的一行调用。
- URL 中的参数名采用前端命名，与后端参数名的转换在 `api/http.ts` 中完成，二者可以独立变化。

**验证**

- 单测：解析与序列化互逆；非法年份、超长关键词、未知类型产生校验错误；修改条件后页码为 1。
- 组件测试：在结果页修改筛选后 URL 中的页码复位。

## ADR-M9-04 创新功能通过注册表接入，合作路径在浏览器端计算

**背景**

- 任务书要求至少一项创新，团队尚未选定（统一 SRS）。成员 1 调研建议评估"合作网络的最短合作路径、中心度"等增强。
- 统计服务按 SPEC-M8-STATS 已提供合作边，不需要新的数据。
- 新增后端接口属于公共契约变更，须成员 1、6 批准。

**候选**

| 候选 | 说明 |
| --- | --- |
| A. 创新页面直接写入路由与导航 | 简单；选题变化时要改多处 |
| B. 注册表 + 构建开关；路径与中心度在后端计算 | 需要新增公共接口 |
| C. 注册表 + 构建开关；路径与中心度在浏览器端用纯函数计算 | 不改公共契约；受浏览器端数据量限制 |

**决策（建议）**

采用 C。`features/registry.ts` 登记创新模块，`VITE_FEATURES` 控制启用；合作路径用广度优先搜索、度中心性在 `domain/collabGraph.ts` 中计算。

**后果**

- 正面：不改公共契约；选题变化或演示故障时可直接关闭；算法可单测。
- 负面：当一次筛选返回的合作边达到数千条以上时，浏览器端计算和传输会变慢。届时改为后端计算，需新增"给定两人返回路径"的公共接口，经成员 1、6 批准；页面只依赖 `ApiClient`，不需要重写。
- 该功能是否构成"创新"由成员 1、6 与老师确认，页面上标注"候选功能"。

**验证**

- 单测：路径的确定性、不连通、起点等于终点、中心度。
- 测试：关闭全部功能后核心路由仍然存在，合作路径路由不存在。
