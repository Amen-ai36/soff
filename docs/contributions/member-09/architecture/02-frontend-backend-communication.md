# 前后端通信架构（成员 9，方案 B）

日期：2026-11-11。阶段：架构设计。分支：`b`。状态：候选设计。

本文规定浏览器与业务服务层之间怎样通信。接口路径、字段名和错误码以成员 8 的 [接口需求约束提案](../../member-08/requirements/03-interface-constraints.md) 为依据；该提案尚未冻结为 OpenAPI，所以本文第 8 节把前端依赖的每一项都列为"假设"，契约冻结后逐项核对。

## 1. 通信方式

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 协议 | HTTPS + JSON，资源风格接口 | 成员 6 部署稿中浏览器只经 HTTPS 访问 ECS 上的 Web/API 单元 |
| 同源 | 前端静态文件与 `/api` 由同一入口提供 | 不需要跨域配置；会话 Cookie 方案可直接使用（待 ARCH9-Q02） |
| 同步/异步 | 浏览器只发同步请求；长任务（采集）由服务端受理后异步执行，前端轮询或刷新查看状态 | 成员 6 ADR-01：长任务不放在线请求内 |
| 开发期 | `ApiClient` 有两个实现：`http`（真实接口）与 `mock`（合成数据） | 后端未完成时前端可独立开发和测试，见 ADR-M9-02 |

浏览器不直接访问 RDS、CSS、OBS。证明材料如需上传，经业务服务层授权后访问 OBS，具体方式待成员 8 确认（其提案第 5 节）。

## 2. 命名与数据转换

线上字段采用成员 8 提案中的下划线写法（`page_size`、`data_version`、`updated_at`），前端内部采用驼峰写法。转换只在 `api/http.ts` 中进行一次：

```text
浏览器内部对象 ──keysToSnake──▶ 请求体 / 查询参数 ──▶ 服务端
浏览器内部对象 ◀──keysToCamel── 响应体 ◀────────────── 服务端
```

这样做的好处是页面和组件代码与线上命名无关；契约若改为驼峰，只改一处。

空值规则沿用成员 8 提案：`null` 表示未知，`[]` 表示无关联，`0` 表示已知为零。转换过程不把 `null` 改成 `0` 或空字符串，显示层再分别呈现为"未提供""无""0"。

## 3. 检索请求

查询参数与成员 8 SPEC-M8-SEARCH 一致：

| 参数 | 前端来源 | 前端校验（不通过则不发请求） |
| --- | --- | --- |
| `q` | 检索框 | 去首尾空白；最长 200 字符 |
| `type` | 类型筛选，可多值 | 只允许 `paper`、`patent`、`project`、`award` |
| `year_from`、`year_to` | 年份筛选 | 1000～9999 的整数；起始不晚于结束 |
| `field_ids`、`institution_ids` | 领域、机构筛选 | 非空字符串 |
| `sort` | 排序 | 成果：`relevance`、`year_desc`、`year_asc`；学者：只允许 `relevance` |
| `page`、`page_size` | 分页 | `page ≥ 1`；`page_size` 1～100，默认 20 |

多值参数用重复键表示（`type=paper&type=patent`），这是假设 A-03。前端校验不能代替服务端校验，只是避免发出必然失败的请求（IA9-RULE-05）。

检索参数同时写在浏览器地址栏中，页面从地址栏读出参数再发请求，因此后退、刷新、分享链接都能还原同一个检索（ADR-M9-03）。

## 4. 错误模型

### 4.1 错误分类

服务端错误响应按成员 8 提案包含机器码、可读消息、追踪 ID 和可选字段错误。前端把所有失败归为下表中的一种，页面只按种类决定显示方式：

| 前端种类 | 来源 | 页面表现 | 可做的操作 |
| --- | --- | --- | --- |
| `INVALID_INPUT` | 400 | 字段旁显示错误，保留其他输入 | 修改后重提 |
| `UNAUTHENTICATED` | 401 | 提示需要登录 | 去登录，登录后回到原页面 |
| `FORBIDDEN` | 403 | 无访问权限 | 返回 |
| `NOT_FOUND` | 404 | 公开内容：不存在；私有内容：与无权限同一句话 | 返回 |
| `CONFLICT` | 409 | 记录已被更新或已有相同申请 | 重新载入最新状态 |
| `RATE_LIMITED` | 429 | 请求过于频繁 | 稍后重试 |
| `DEPENDENCY_UNAVAILABLE` | 503 | 服务暂时不可用，显示追踪 ID | 重试 |
| `TIMEOUT` | 前端计时到期 | 请求超时 | 重试 |
| `NETWORK` | 浏览器网络错误 | 网络连接失败 | 重试 |
| `UNKNOWN` | 其他状态码或无法解析的响应 | 未知错误，显示追踪 ID | 重试 |

### 4.2 三条约束

1. **业务空结果不是错误。** 检索返回 `total = 0` 走"空结果"分支；服务失败走错误分支，绝不显示成"0 条结果"（EX9-R-01）。
2. **私有资源的"无权"和"不存在"对用户说同一句话。** 成员 8 提案已规定无权读取私有申请时返回 404；前端对私有上下文中的 403 与 404 也使用相同文案，不通过提示差异暴露资源是否存在（EX9-R-03）。
3. **不展示服务端原始错误正文。** 页面只显示前端按种类生成的文案与追踪 ID，避免把堆栈或内部信息带到界面上（UI9-NFR-04）。

## 5. 超时、取消与重复请求

| 场景 | 做法 | 实现位置 |
| --- | --- | --- |
| 单个请求超时 | 默认 10 秒，超时归为 `TIMEOUT` | `api/http.ts` |
| 连续修改检索条件 | 新请求开始时取消上一个；迟到的旧响应被丢弃，只显示最后一次请求的结果 | `composables/useAsync.ts` |
| 离开页面 | 取消该页面未完成的请求 | `useAsync.ts` 在作用域销毁时取消 |
| 提交按钮连点 | 提交进行中时忽略再次点击 | `composables/useSubmit.ts` |
| 网络抖动后重试提交 | 同一表单实例重用同一个 `request_key`，服务端按成员 8 提案返回已有结果，不会产生两个申请 | 认领申请页、审核页 |

10 秒是前端默认值，不是性能指标；后端给出实际 P95 后可调整。

## 6. 并发与权威状态

认领审核和门户维护是会被多人同时修改的数据。成员 8 提案要求写请求携带 `expected_version`，版本不一致返回 409。前端的处理：

```text
提交（带 expected_version）
  ├─ 成功 → 用响应中的新状态和新版本刷新页面
  └─ 409 CONFLICT → 提示"记录已被更新"，重新读取最新数据，保留用户已填写但未提交的内容
                   不自动重试，由用户看过最新状态后决定
```

写操作成功后前端不自行推断结果状态，一律以服务端返回为准（FS9-BR-02）。通知类失败（例如邮件未发出）不改变页面上已提交成功的状态（FS9-BR-03）。

## 7. 会话与权限

SPEC-M8-AUTH 尚未选定会话机制（Cookie 还是令牌），前端按以下最小假设设计，选型后只改 `api/http.ts`：

- 请求设置 `credentials: 'same-origin'`；不把任何令牌放入 URL、`localStorage` 或日志。
- 预留 CSRF 头的注入函数，若选用 Cookie 方案则启用。
- 页面通过 `GET` 会话接口得到当前用户与角色，只用于决定显示哪些入口。
- 路由守卫只做引导：未登录访问"需登录"页面时跳转登录页，并把原地址作为回跳参数；回跳地址只接受站内路径（`domain/redirect.ts`）。
- 已登录但没有权限的用户进入管理页时，页面照常请求，由服务端返回 403，页面显示"无访问权限"。这样权限只有服务端一处判断。
