# A/B 数据管道对比与 ADR 决策依据

成员 7 · 2026-11-16。供成员 6（ADR 主编）、成员 1（复核）编写统一 ADR，比较范围限定在数据接入与发布链路。A 组内容引自成员 2 [方案 A 架构正文](https://github.com/Amen-ai36/soff/blob/3d90727/docs/contributions/member-02/architecture/01-data-pipeline-architecture.md)与[决策材料](https://github.com/Amen-ai36/soff/blob/3d90727/docs/contributions/member-02/architecture/02-architecture-decision-inputs.md)，不代写 A 组决定。

## 1 共同点

两组基本架构一致，不应写成互斥方案（与成员 6 调研报告 §4 的判断相同）：控制端与执行端分离；持久任务账本 + 租约/执行代次；有界批次事务；批次检查点与公开发布水位分离；事务 outbox 驱动投影；同版本 ID 集合核验后条件切换公开指针；撤回经权威公开策略即时生效。

## 2 差异

| 比较项 | 方案 A（成员 2） | 方案 B（本稿） | 共同测量 |
| --- | --- | --- | --- |
| 发布单元 | 以 outbox 事件为主驱动候选投影，再按数据版本核验发布 | 以**候选版本**为一等对象：先冻结 V、U 和预期公开 ID 集合，outbox 只用于增量填充隔离候选代次 | 候选落库到可公开耗时、补偿范围、ID 差异 |
| 任务状态 | 含 QUEUED、PARTIAL_SUCCESS；STOPPED 可由管理员显式恢复 | PENDING…SUCCEEDED 七态；无 PARTIAL_SUCCESS；STOPPED 终态，重跑新建任务引用旧任务；FAILED 显式 retry 增加 attempt | 停止生效边界、恢复耗时、重复与漏处理数 |
| 阶段记录 | DISCOVER→…→FINALIZE 八阶段 | RUNNING 下四个 stage：FETCH / PROCESS / SAVE / AWAIT_PUBLISH | 管理端可理解性（成员 9 评估） |
| 非法强标识 | 进入治理 | 隔离，不清空后继续弱匹配 | 同一夹具下隔离数与误合并数 |
| 弱匹配 | 按样本校准阈值处理 | 只生成复核事项，不自动合并 | 误合并、漏合并、人工队列规模 |
| 来源并发 | `source_id + scope_hash` 写互斥 | 同上，另默认每来源一个执行者 | 限流违规数、来源配额利用 |
| 撤回 | 更新权威公开策略后排队同步 | 同事务递增公开栅栏 epoch（沿用成员 8 方案） | 撤回后残留暴露、阻断时长 |

## 3 ADR 依据

### ADR-M7-01 数据库任务账本 + 租约令牌，不引入消息中间件（Proposed）

- **背景**：采集是长任务，受来源限流；课程团队运维能力有限；业务 API 不能被抓取阻塞。
- **候选**：① API 请求内同步执行；② 关系库任务账本 + 独立工作进程轮询领取；③ 独立消息中间件（如 Kafka/RabbitMQ）编排阶段。
- **建议**：选②。任务状态、批次提交和执行权都在同一权威库，条件写即可保证单一有效写入者；不增加部署组件。
- **后果**：需要处理轮询负载、租约时长和积压监控；吞吐上限受数据库约束。
- **何时重新评估**：实测出现入队延迟或轮询负载成为瓶颈时，再引入队列，但令牌校验与幂等规则不变。
- **验证**：F-01～F-03（见 02 §5）。

### ADR-M7-02 候选版本优先发布，outbox 作为增量投影通道（Proposed）

- **背景**：数据库与索引无共同事务；只比较条数无法发现"同数不同集"；成员 8 已提出 outbox 与公开栅栏。
- **候选**：① 批次直接同步双写；② 纯 outbox 事件驱动，事件处理完即视为可发布；③ 先形成候选版本，outbox 增量填充隔离代次，集合核验后条件切换。
- **建议**：选③。outbox 解决"业务写入与待投影事件"的一致性，候选版本解决"发布什么"的一致性，两者职责分开；全量重建作为回退路径。
- **后果**：多一个候选版本对象与冻结步骤；发布延迟包含核验时间；需要保留旧代次直到无引用。
- **验证**：F-07～F-09。

### ADR-M7-03 检查点与水位分离、停止不可恢复（Proposed）

- **背景**：长任务中断需要恢复；未发布的数据不能成为下一轮增量起点；停止需要明确语义。
- **候选**：① 单一水位随批次推进；② 单一水位只随发布推进；③ 候选检查点 + 发布水位双进度。停止语义另有：可恢复（A）/ 终态重跑（B）。
- **建议**：采用③；STOPPED 为终态，重跑新建任务并通过"来源键 + 哈希"幂等复用已提交观测。
- **后果**：要保存并展示两类进度；重跑会重新请求来源（受限流约束），换来更简单的状态机与审计。
- **验证**：F-02、F-08、F-10，并与 A 组在同一停止点比较恢复耗时与重复请求数。

以上三条为 B 组岗位依据，正式 ADR 编号与是否采纳由成员 1、6 共同决定；本稿不预填 Accepted。

## 4 同口径比较方法

使用同一冻结 manifest、同一模拟标记与字段许可样例、同一故障注入点与资源环境，分别报告：每分钟有效处理记录数、候选提交到公开的延迟、恢复后重复数、同版本 ID 差异、去重与作者消歧 Precision/Recall/F1（人工独立标注，零分母报"不适用"）。每项保留数据版本、环境、测量区间与分母。目前两组都没有运行数据，不填优胜结论。
