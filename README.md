# 学术成果分享平台

本仓库用于《软件系统分析与设计》课程实践。项目采用双组并行开发方式：两个小组使用不同的 AI 模型，分别实现相同的核心功能，最终通过统一验收选择主版本，并吸收另一实现中的优秀模块。

## 分支说明

| 分支 | 负责人 | 用途 |
| --- | --- | --- |
| `main` | 全体成员 | 公共规范、统一阶段交付物、公共契约及最终合并版本 |
| `a` | 成员 1～5 | A 组使用模型 A 完成的候选实现 |
| `b` | 成员 6～10 | B 组使用模型 B 完成的候选实现 |

`a` 和 `b` 从同一个初始提交建立。两组可以采用不同的架构、算法、界面方案和创新功能，但必须遵守相同的核心需求、公共数据语义、API 契约和验收标准。

## 统一交付原则

课程阶段交付物只提交一份，由两个小组共同完成：

- 需求调研报告及 PPT。
- 系统需求规格说明书（SRS）、UML 和核心模块 SPEC。
- 需求分析文档及 PPT。
- 架构调研报告、架构设计说明书、ADR 及 PPT。
- 数据库、接口、UI 和其他构件设计说明。
- 测试报告、部署说明和答辩 PPT。
- Agentic Coding 使用证据和双模型对比材料。

两组存在差异的内容应写入同一份交付物的“方案 A”“方案 B”或附录中，不能分别提交两套正式课程文档。详细分工参见 [双组并行开发与合并方案.md](双组并行开发与合并方案.md)。

## 核心功能

两个候选实现均须完成：

1. 用户认证、角色和权限管理。
2. 论文、专利、科研项目、获奖等成果的数据采集或导入。
3. 数据清洗、标准化、去重、作者消歧和机构归一化。
4. 不少于 10,000 条学术成果数据入库。
5. 成果检索、过滤、分页、排序和详情查看。
6. 学者门户、门户认领、管理员审核和成果维护。
7. 采集任务创建、运行、失败重试、停止和状态查看。
8. 机构排名、成果类型和领域分布等基础统计分析。
9. “采集 -> 清洗 -> 入库 -> 检索 -> 统计分析”完整链路。
10. 至少一项创新功能。

## 协作流程

1. 公共需求、数据模型、OpenAPI、错误码和验收测试先在 `main` 中确定。
2. `a`、`b` 定期同步 `main`，不得单方面修改公共契约。
3. 每个核心模块必须先有 SPEC，再由成员或 AI 编写代码。
4. 两组分别在自己的分支完成开发、测试和部署验证。
5. 阶段交付物由对应岗位成员共同撰写，再合入 `main`。
6. 中期至少进行两次接口和模块替换试验，不能把第一次集成留到最后。
7. 最终使用同一数据集和公共测试评价 `a`、`b`。
8. 选择综合质量更高的实现作为主版本，在 `main` 中逐模块吸收另一组的优点。

## Git 注意事项

- 禁止在 `main` 上直接进行未经评审的功能开发。
- A 组只向 `a` 提交候选实现，B 组只向 `b` 提交候选实现。
- 公共契约变更必须由成员 1 和成员 6 共同确认。
- 提交应小而明确，避免全项目格式化、批量改名和无关重构。
- 不得擅自升级主要依赖或更换框架。
- 数据库迁移必须使用唯一编号，并说明向前和回滚影响。
- 密钥、令牌、真实账号和敏感数据不得提交到仓库。
- 合并前必须通过公共契约测试和回归测试。

## AI 使用要求

- A 组开发阶段使用模型 A，B 组开发阶段使用模型 B。
- AI 只能修改任务明确指定的模块和文件。
- AI 不得擅自修改公共 API、业务实体、数据库基础结构或依赖版本。
- 所有 AI 生成代码必须经过人工审查和测试。
- 提示词、模型版本、生成内容、人工修改和测试结果必须留痕。
- 两组均需提供“AI 生成 -> 人工修正”案例，最终形成一份统一对比记录。

完整智能体约束参见 [AGENT.md](AGENT.md)。符合课程要求及智能体自动发现约定的入口文件为 [AGENTS.md](AGENTS.md)。

## 数据与合规

- 优先使用 OpenAlex、DBLP 等公开数据源或课程提供的模拟数据。
- 不爬取收费数据库、个人隐私或未获授权的数据。
- 采集程序必须设置限速、失败重试、来源记录和停止机制。
- 原始数据、清洗结果和生成数据应能够追溯来源和处理过程。
